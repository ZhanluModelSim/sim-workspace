# DES 执行模型、穿刺结论与后续开发建议

本文补充主架构方案，供后续设计和开发使用。状态：已完成独立原型穿刺；正式平台实现尚未开展。代码、快照和结果见 [原型报告](des-prototype/README.md)，整体仓库方案见 [架构与协同开发方案](架构与协同开发方案.md)。

## 1. 问题与目标

纯 tensor 数据 DAG 只描述部分先后约束，不足以唯一决定执行顺序和性能。按 topo 层级、同层 ID 排序，可能让后层无源节点过早竞争资源；topo 层级也不能自动变成整层完成屏障。

当前优先目标是可解释、确定、符合逻辑执行约束的调度，先解决不合理的提前执行，再讨论并发利用率；不搜索全局最优拓扑排列。

仅给 ready 节点增加优先级不够：早期节点等待通信时，后层无源节点可能是唯一 ready 的工作。因此需要同时定义执行资格和资源仲裁。

## 2. 建议执行模型

明确分离三层：

1. **执行约束**：数据／mutation 依赖、逻辑 stream 顺序、event/wait、必要的提交或释放条件。
2. **资源需求**：CUBE、VEC、COMM 等容量与节点资源需求；逻辑 stream 不等于硬件资源。
3. **仲裁策略**：从当前 eligible 且资源可满足的节点中，按捕获 `seq_idx` 优先、ID 平局规则启动。

节点状态为：未释放 → 等待依赖／队列 → ready → running → done。首版忽略 Host 下发耗时，不伪造绝对提交时间戳；保留捕获顺序和执行约束。后续若需刻画 Host 瓶颈，再增加提交耗时和同步模型。

已有 stream/event 关系优先使用。普通设备节点确实缺少流时，可以在明确证据下映射到默认逻辑队列；不能仅凭“通信算子”分类就虚构独立异步流。回退产生的边须标记来源为假设。

**原型的限制：**无流设备节点归入独立 `unknown-device` 队列，仅保证该队列内部顺序，无法证明它与已知流的关系。四组实测中此回退节点为 0，不能据此宣称已验证通用缺流场景。正式版本应要求显式回退策略或报告信息不足。

## 3. 事件循环与资源分类

执行循环：

```text
处理当前时刻全部完成事件，释放资源
  → 更新依赖计数与同步状态
  → 零资源节点传播到不动点
  → 在 ready 中选择资源满足的节点并启动
  → 将完成事件加入时间堆
  → 推进到下一事件
```

不得按 topo 层级等待无关节点；不得让等待依赖的节点提前占用计算资源；多个资源应原子获取。一个节点缺少 CUBE 时，不应阻挡可独立执行的 VEC 节点。

| 类型 | 首版处理 | 需要保留的边界 |
| --- | --- | --- |
| view/alias/detach、Host 标记 | 不占设备计算资源 | 保留依赖；忽略 Host 成本是显式假设 |
| empty 等未初始化分配 | 不占 CUBE/VEC | 不据此推导真实分配时刻或内存峰值 |
| wait/event | 零耗时控制节点 | 等待未满足时不能通过 |
| copy、fill、初始化 | 计入设备工作 | 不和 empty 混淆；DMA 可后续细化 |
| 矩阵、向量、通信 | 分配相应资源 | 分类需结合实际 kernel 与成本模型 |
| 混合 kernel | 可表达多个资源需求 | 原型全程原子占用仅为粗粒度近似 |
| 未识别节点 | 显式标记并采用配置化回退 | 不静默按零耗时忽略 |

## 4. 实际穿刺结果

使用当前训练仓库完整 L0 源图（不是隐藏 FSDP 工作的投影视图），模型为 DSV4/Kimi smoketest；world=4、DP replicate=2、EP=2、rank=0、seq_len=128，量化关闭。

| 模型 | AC | L0 节点数 | FSDP 通信忙时中与模型计算重叠的比例 |
| --- | --- | ---: | ---: |
| DSV4 | none | 5,369 | 37.5% |
| DSV4 | selective | 7,012 | 37.5% |
| Kimi | none | 4,106 | 51.6% |
| Kimi | selective | 5,438 | 46.9% |

时间使用人为指定的 synthetic ticks。以上比例不是硬件实测、模型加速比或性能预测精度结论。

已验证：

- 四组全部节点完成；前驱约束和资源互斥检查通过。
- 保留既有逻辑流和事件后，四组均不需要增加队列边，且有 FSDP 通信／模型计算重叠。
- 每组延长一个有模型后继的 AG、RS、AR 各 1000 ticks，共 12 次检查，下游选定计算开始时间均延后 1000 ticks。
- 通信耗时按 0.5 倍／2 倍变化后，四组仍有非零重叠。
- 6 项最小测试通过，包括“优先级不能阻止后层无源任务、队列顺序可以”的反例。

未验证：真实硬件耗时、完整规模模型、FP8／其他量化、Host 提交速率、内部隐藏流、多 rank 网络与 collective rendezvous、重调度后的内存生命周期、全局最优调度。

原型仍有未精细分类节点，采用显式 VEC 回退；融合与卷积的多资源映射也是假设。不能直接将原型分类表作为正式硬件算子契约。

## 5. 不强制引入通用 DES 框架

当前已知 DAG、固定资源、不可抢占、启动前确定耗时的范围内，建议采用专用 Python DES 内核，无需强制依赖 SimPy 或 salabim。

通用接口可直接对应为：资源容量表、可启动性检查、完成时间堆、完成时释放资源、依赖计数与 ready 队列。不必为每个算子建立 generator/process，也不必为 request/release 等构造额外通用事件对象。

这可能减少对象、回调和调度开销，但**没有进行同语义框架对比，不能声称已经比 SimPy/salabim 更快**。算法、数据布局和是否反复扫描全图比“是否使用第三方库”更重要。

建议正式模块分工：

| 模块 | 职责 |
| --- | --- |
| ExecutionModel | 节点、执行依赖、资源需求、耗时；接收 G 的执行转换结果 |
| Scheduler | eligible 选择、资源仲裁和策略解释 |
| EventLoop | 时间推进、事件批处理、状态更新 |
| Recorder | 时间线、等待原因和统计；可配置记录粒度 |

分类、Costmodel 调用、模型专属后处理放在内核外。内核不判断 DSV4/Kimi 或某层 FSDP。保持平台单发行包结构，不因上述职责划分新增独立发行包。

仅当后续大量需要动态进程、取消／中断、抢占、随机到达和复杂过程交互时，再重新比较通用框架的收益。专用内核也不应逐渐复制一整套通用仿真框架。

## 6. 后续开发计划与验收门槛

| 阶段 | 工作 | 验收 |
| --- | --- | --- |
| 1：接口与语义 | 明确 G 到 ExecutionModel 的转换、依赖种类、逻辑流来源、回退策略、时间单位、未知成本 | 区分捕获事实和建模假设；缺失引用、循环和非法资源需求可诊断 |
| 2：生产化 L1 内核 | 从原型整理事件循环、资源容量、确定性策略和 Recorder | 小案例独立预期、同刻事件、零耗时闭包、多资源原子获取、无饥饿保证范围、死锁诊断 |
| 3：成本与分类接入 | 用 Costmodel 替换假设耗时，完善 copy/初始化/融合及未知节点分类 | 不把未知当零；版本、单位、资源需求可追溯；错误分类有明确告警 |
| 4：规模与性能基准 | 固定捕获快照、不同节点／边／流数量、重复调度和批量任务 | 分开测解析、准备、调度、记录、导出；报告墙钟时间、峰值内存和结果一致性 |
| 5：L2 扩展 | 多 rank 实例、collective 匹配、调度图及网络资源 | 匹配不全可诊断，延迟传播正确，不将单 rank COMM 当作完整网络模拟 |
| 6：真实轨迹校验 | 代表性配置对照实际设备轨迹 | 区分提交模型、资源模型、成本预测误差，不为贴合单条轨迹添加无依据边 |

性能基准先建立专用内核自身的基线；确有选型需求时再与第三方框架进行等价模型比较。原型总耗时不能当作正式吞吐承诺。

## 7. 集成到已有平台计划

主架构中的“最小 DES”阶段可使用本原型作为行为参考；输入 JSON、6 项测试和四组结果是回归素材，不直接复制成公共 G schema。

L1 结果修正规则仍按主方案执行。若修改节点耗时，应重新运行相应 L1 推演，而非只修改总耗时；保留修正前后结果。运行器与组件版本仍由平台集成清单单向锁定。

本次不修改训练仓库，不提交原型。评审批准执行语义后，再在 SIMPlatform 的 `src/sim_platform/des/` 内实现生产版本。
