# 公共协作与文档规范

管理仓组织跨仓协作，各业务仓保持独立开发、安装和发布能力。本规范只定义资料归属与协作方法，不代替组件接口或测试规范。

| 内容 | 维护位置 |
| --- | --- |
| 工作区获取与仓库导航 | 根 README |

README 做导航，AGENTS 做规则，专题解释机制；不要将同一完整实现说明复制到三处。组件已有能力与平台已完成接入分开描述，跨仓摘要以链接为主。

## 更新与历史处理

- 文档优先中文，保留实际代码符号与名称；仓库使用小写连字符，导入包使用下划线。
- 用户新确认覆盖旧建议。改动责任边界时更新当前规范，不在末尾追加一段“替代前文”而留下相互冲突的规则。
- 状态以实现及相应验证为依据；已确认需求、已实现、已验证与待定分开表达。发现业务仓文档漂移时标出真实依据，跨仓任务不擅自替组件制定未定语义。
- 待办写清负责方和待确认点，不把旧仓功能、原型建议或空接口当成已批准范围。完成后移出待办，并链接组件实现/验收。
- 不累加每轮测试数量、临时日志路径和实验数字作为当前状态。历史报告从 Git 或明确的制品记录追溯；需要复现时使用精确提交、环境及原始证据。
- 删除历史中间文档前，将仍有效的约束/经验迁入所属主题，更新引用。`docs/bootstrap/` 整体保留为历史启动材料，导航明确非现行规范；原始数据、假设、相对链接不随最新实现改写。
- 跨仓相对链接适用于已克隆的工作区，并提供仓库远端导航；精确验收来源使用固定 revision，日常使用指南可链接当前组件文档。不要把本机绝对路径写成团队前提。

## 跨仓执行与版本

开始前检查各目标仓的分支、HEAD、工作树和适用规则，保留已有改动。确认生产者、消费者及接口迁移影响；实际运行时核对导入路径，不能假定共享目录等于共享环境。

各业务仓独立提交/发布，根仓不纳入业务目录或 gitlink。平台单向验证组合；开发覆盖记录实际路径/SHA/dirty 状态，不能伪装为正式锁定。先验证候选组合，再按组件到平台顺序交付，最终组合需完成相应检查。

不提交凭据、个人环境和未说明的运行产物。公共 agent 资料不等于工具会自动加载的技能，按其声明方式使用。分工、单写入者和独立 review 遵循[推荐工作流](../.agents/workflows/multi-agent-development.md)。

## 验证与交付

纯文档修改检查事实、路径、相对链接/锚点、Git 纳入范围及其他仓状态；无需触发训练测试。代码或行为修改按各仓规范验证，区分静态检查、Meta 捕获、synthetic 调度和真实硬件精度。

报告说明修改范围、验证和未完成边界。提交/推送须符合当次授权，各仓分别操作；管理仓的提交或 bundle 不包含被忽略的业务源码、未提交内容或运行环境。
