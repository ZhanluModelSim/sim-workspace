# 多仓协作推荐工作流

本工作流适用于 sim-workspace 及其业务仓库，作为后续开发的默认推荐方式：主 agent 负责需求讨论、总体设计、任务拆分、review 和集成验收；子 agent 按边界明确的任务承担局部工作。是否委派取决于任务的独立性与收益，不要求每个仓库始终配置一个 agent。

## 当前阶段

已进入训练优先的渐进开发阶段；需求和架构中的未决部分，必须由主 agent 与用户直接明确目标、边界及未决问题，不将需求确认或跨仓决策委派出去。不启动各仓自行设计、各自补齐假设的并行建设。

只有具体任务的目标、修改范围、依赖条件和验收方式足够明确后，才进入委派实施。已明确的局部任务可以推进，不必等待全项目所有设计冻结；尚未确定的需求继续保持未决状态，尤其不替推理侧预定输入、输出或仿真粒度。

## 角色分工

| 角色 | 职责 |
| --- | --- |
| 主 agent | 与用户讨论需求，维护确认事项，协调跨仓接口和依赖，拆分任务，检查实际变更，组织集成验证，汇总交付 |
| 实施子 agent | 阅读适用规则与源码，在分配范围内完成具体任务和验证，报告发现、变更、证据及未完成项 |
| 独立审查子 agent | 对关键变更检查语义、消费者、测试依据与遗漏，提出可核实的意见；审查任务默认不修改代码 |

训练捕获、预测模型、平台适配、DES 或指标等可以形成领域任务，但“负责一个仓库”不能代替具体交付要求。主 agent 保持总体技术理解，不能仅转发子 agent 的结论。用户在主对话中给出的修正，由主 agent 同步到相关任务与文档。

## 何时采用单 agent

以下工作通常由主 agent 直接完成：

- 当前阶段的需求讨论、方案取舍和边界确认。
- README、小范围文档、初始化及常规 Git 操作。
- 前后步骤紧密依赖、拆分后需要频繁往返确认的任务。
- 多人会争用同一文件、分支或运行环境，且隔离成本高于并行收益的工作。

对能够独立完成的实现、源码调查、验证或审查任务，按需启用子 agent。优先从主 agent 加一至两个子 agent 开始，根据任务规模、协调成本与实际可用能力调整，不固定并发数量，也不强制每次开发都委派。

## 派发前明确任务

主 agent 先检查有关仓库状态、适用 AGENTS.md 和当前决策，再给出足够独立执行的任务说明。复杂任务可使用以下清单；简单任务不必机械填表：

- **目标与交付件**：需要解决什么问题，交付代码、分析还是审查意见。
- **输入与依据**：相关文档、源码基线、已确认语义及必要的生产者／消费者。
- **范围与归属**：允许修改的仓库、目录或文件，当前负责人及分支／工作树位置。
- **明确排除项**：不自行改变的接口、假设和仍待用户明确的问题。
- **验收条件**：可观察的预期行为、需要执行的检查，以及本轮不覆盖的范围。
- **协作边界**：共享环境使用方式、依赖其他任务的条件，以及提交和推送由谁执行。

不要将整个聊天历史当作唯一任务说明。发现跨仓接口需求或超出范围的问题时，子 agent 向主 agent 提供具体证据和建议，由主 agent 协调后续处理；不自行扩展修改范围或冻结公共契约。

## 实施与共享状态

每份可变内容同一时间只安排一个写入者。主 agent 在委派期间也不同时编辑该子 agent 正在修改的文件。不同 agent 不默认拥有独立文件系统或运行环境。

同仓确需并行写入时，优先使用独立分支／worktree，并明确最终集成方式。不同仓库也要协调共享容器、editable 安装、全局配置、输出目录和测试进程，避免源码隔离但环境互相覆盖。

子 agent 按任务执行组件规则和必要验证，保留失败信息。不要通过放宽校验、补造数据或扩大假设，使结果看起来通过。正常实现选择在已授权范围内自主完成；影响需求和跨仓语义的取舍反馈给主 agent。

## Review 与集成验收

子 agent 完成后交付变更文件或提交、关键设计理由、实际验证命令与结果，以及已知限制或阻塞项。未执行的检查明确标注，不能将历史验证当作本轮结果。

主 agent 检查实际 diff、相关调用方和测试证据，确认没有越过职责边界，并核对用户最新决定。不能仅依据执行者的“完成”总结验收。

对调度语义、通信归属、生命周期、缓存正确性或公共接口等重要改动，可增加未参与实现的独立审查。主 agent 核实审查意见、协调修正，再执行与变更相称的跨仓集成检查；已有检查通过且没有新变化时，不为形式重复运行昂贵测试。

提交、合入和推送由主 agent 统一协调，按用户实际授权执行；本工作流本身不授予新的远端操作权限。跨仓版本组合遵循平台单向集成的现有约定，子 agent 不各自发布未经集成的组合。

## 交接与知识沉淀

主 agent 将确认后的跨仓决定记入管理仓，组件内部事实和使用方式记入对应仓库。未决事项保留为未决，不把任务中的临时假设提升为约定。

文档、提交和验证证据应使新的 agent 能接手工作；不依赖某个长期会话的记忆。保持领域分工可以减少重复阅读，但不把知识绑定在某个子 agent 上。

最终由主 agent 向用户说明整体完成情况、各仓影响、验证结果和仍需明确的事项，不把多个局部成功直接等同于端到端完成。

## 本轮实践形成的验收顺序

先用真实小负载核对字段与边界，再按单写入者分配适配器、预测、DES 等任务；主 agent 负责公共契约和入口集成。组件交付附实际测试证据，独立 reviewer 只读审查并给出触发条件。修复后增加能复现问题的测试并复核，最后完成跨仓系统与 wheel 安装验证。已通过且未受后续改动影响的检查不机械重跑。通用代码习惯见 [Python 开发与验收规范](../standards/python-development.md)。
