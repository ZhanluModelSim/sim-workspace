# 多仓协作推荐工作流

本工作流适用于 sim-workspace 及其业务仓库，作为后续开发的默认推荐方式：主 agent 负责需求讨论、总体设计、任务拆分、review 和集成验收；子 agent 按边界明确的任务承担局部工作。是否委派取决于任务的独立性与收益，不要求每个仓库始终配置一个 agent。

## 需求与决策

需求和架构中的未决部分，由主 agent 与用户直接明确目标、边界及未决问题；可委派调查和方案分析，但需求确认与跨仓决策仍由主 agent 负责。不启动各仓自行设计、各自补齐假设的并行建设。

只有具体任务的目标、修改范围、依赖条件和验收方式足够明确后，才进入委派实施。已明确的局部任务可以推进，不必等待全项目所有设计冻结；尚未确定的需求继续保持未决状态，尤其不替推理侧预定输入、输出或仿真粒度。

## 角色分工

| 角色 | 职责 |
| --- | --- |
| 主 agent | 与用户讨论需求，维护确认事项，协调跨仓接口和依赖，拆分任务，检查实际变更，组织集成验证，汇总交付 |
| 实施子 agent | 阅读适用规则与源码，在分配范围内完成具体任务和验证，报告发现、变更、证据及未完成项 |
| 独立设计 reviewer | 检查目标、方案、职责边界、接口、迁移和验证计划；不参与被审设计的编写 |
| 独立实现 reviewer | 检查最终代码、消费者、回归风险、测试有效性和设计落实情况；不参与被审代码的实现 |

训练捕获、预测模型、平台适配、DES 或指标等可以形成领域任务，但“负责一个仓库”不能代替具体交付要求。主 agent 保持总体技术理解，不能仅转发子 agent 的结论。用户在主对话中给出的修正，由主 agent 同步到相关任务与文档。

## 何时采用单 agent

以下工作通常由主 agent 直接完成：

- 当前阶段的需求讨论、方案取舍和边界确认。
- README、小范围文档、初始化及常规 Git 操作。
- 前后步骤紧密依赖、拆分后需要频繁往返确认的任务。
- 多人会争用同一文件、分支或运行环境，且隔离成本高于并行收益的工作。

对能够独立完成的实现、源码调查、验证或审查任务，按需启用子 agent。优先从主 agent 加一至两个子 agent 开始，根据任务规模、协调成本与实际可用能力调整，不固定并发数量，也不强制每次开发都委派。

## 按风险选择流程

新功能、较大重构及涉及公共接口、跨仓职责、调度、通信、生命周期或缓存语义的改动，采用以下完整流程：

| 阶段 | 主要负责人 | 交付与通过条件 |
| --- | --- | --- |
| 需求与设计 | 主 agent | 明确目标、非目标、边界、接口、兼容迁移、验证方案及未决事项 |
| 设计 review | 独立设计 reviewer | 核查方案能否解决需求、复杂度和遗漏；主 agent 核实并解决阻塞问题后进入受影响部分的实施 |
| 实现与自测 | 实现 agent 或主 agent | 按已审设计实施，提供实际 diff、自测证据、已知限制及设计偏离说明 |
| 实现 review | 独立实现 reviewer | 核查代码行为、设计落实、消费者及回归证据；修复后复核受影响结论 |
| 集成与验收 | 主 agent | 对照需求、设计和最终代码检查完整结果，完成必要组合验证并协调 PR 交付 |

主 agent 全程统筹：派发前明确接口和验收条件，实施期间处理偏离与依赖，最后对整体结果负责，不是到最后才接手。设计可以写在已有设计文档、任务或 PR 中；没有独立文档需求时不强制新增文件。

流程按任务风险和规模裁剪，不强制每次派发实现 agent，也不要求每次安排两位不同 reviewer。小范围修复可用简短设计说明，风险较低且方案直接时可省独立设计 review；纯文档、格式及机械修改通常由主 agent 完成相称的事实、链接和 diff 检查。重要实现仍需未参与实现者的独立 review；不能因为由主 agent 亲自实现而改为自审。简化的阶段及未覆盖风险在交付中说明，不逐项申请流程豁免。

同一个 reviewer 可以先审设计再审实现，以跟踪方案落实；前提是不参与对应设计或代码的编写。高风险改动可增加另一位独立实现 reviewer，不固定角色人数或并发数量。独立 review 不可用实现者自查冒充；工具或人员不可用时说明未完成项。

## 派发前明确任务

主 agent 先检查有关仓库状态、适用 AGENTS.md 和当前决策，再给出足够独立执行的任务说明。复杂任务可使用以下清单；简单任务不必机械填表：

- **目标与交付件**：需要解决什么问题，交付代码、分析还是审查意见。
- **输入与依据**：相关文档、源码基线、已确认语义及必要的生产者／消费者。
- **范围与归属**：允许修改的仓库、目录或文件，当前负责人及分支／工作树位置。
- **明确排除项**：不自行改变的接口、假设和仍待用户明确的问题。
- **验收条件**：可观察的预期行为、需要执行的检查，以及本轮不覆盖的范围。
- **协作边界**：共享环境使用方式、依赖其他任务的条件，以及提交和推送由谁执行。

不要将整个聊天历史当作唯一任务说明。发现跨仓接口需求或超出范围的问题时，子 agent 向主 agent 提供具体证据和建议，由主 agent 协调后续处理；不自行扩展修改范围或冻结公共契约。

## 实施与共享状态

每份可变内容同一时间只安排一个写入者。主 agent 在委派期间也不同时编辑该子 agent 正在修改的文件。不同 agent 不默认拥有独立文件系统或运行环境。

同仓确需并行写入时，优先使用独立分支／worktree，并明确最终集成方式。不同仓库也要协调共享容器、editable 安装、全局配置、输出目录和测试进程，避免源码隔离但环境互相覆盖。

子 agent 按任务执行组件规则和必要验证，保留失败信息。不要通过放宽校验、补造数据或扩大假设，使结果看起来通过。正常实现选择在已授权范围内自主完成；影响需求和跨仓语义的取舍反馈给主 agent。

## Review 闭环与集成验收

子 agent 完成后交付变更文件或提交、关键设计理由、实际验证命令与结果，以及已知限制或阻塞项。未执行的检查明确标注，不能将历史验证当作本轮结果。

主 agent 检查实际 diff、相关调用方和测试证据，确认没有越过职责边界，并核对用户最新决定。不能仅依据执行者的“完成”总结验收。

设计 review 关注目标覆盖、职责归属、接口与迁移、失败路径、复杂度及验证方案；实现 review 直接检查最终 diff 和相关源码，关注实际行为、消费者、回归风险及测试是否证明需求，不只检查格式或设计文档。reviewer 默认只读，提出证据和建议，由实现者修复，避免参与实现后再自审。

每轮 review 明确被审提交或 diff 范围，并区分阻塞问题、非阻塞建议和未验证项。意见应给出位置、触发条件、影响和依据；没有发现问题时也说明检查范围及限制。主 agent 核实意见并协调修复，记录采纳、修复或不采纳的理由；涉及需求取舍时再由用户确认。阻塞问题须解决并复核后，才能进入依赖它的下一阶段；不受影响的独立工作可以继续。

实现若实质改变公共接口、跨仓职责、调度／缓存／生命周期语义或关键算法假设，应由主 agent 更新设计并补设计 review；普通实现细节不重复走完整流程。后续修改影响原审查结论时，对受影响范围复核，不把旧版本“通过”沿用到新 diff。

主 agent 最终核对需求覆盖、设计偏离、review 闭环、实际提交及生产者／消费者精确组合，再执行与变更相称的集成验证。局部测试通过不替代组合验收，review 也不替代测试；已有检查通过且未受新变化影响时，不为形式重复运行昂贵测试。

提交、合入和推送由主 agent 统一协调，遵守[独立分支与 PR 交付规则](pr-only-development.md)：任务分支开发并提 PR，不直接推送约定集成分支。按用户实际授权执行；本工作流本身不授予新的远端操作权限。跨仓版本组合遵循平台单向集成的现有约定，子 agent 不各自发布未经集成的组合。

需要关联跨仓候选、比较改进效果或沉淀任务方法时，使用[轻量 RSI 工作流](lightweight-rsi.md)及其 ChangeSet 模板；人员分工与交付授权仍以本流程为准。

## 交接与知识沉淀

主 agent 将确认后的跨仓决定记入管理仓，组件内部事实和使用方式记入对应仓库。未决事项保留为未决，不把任务中的临时假设提升为约定。

文档、提交和验证证据应使新的 agent 能接手工作；不依赖某个长期会话的记忆。保持领域分工可以减少重复阅读，但不把知识绑定在某个子 agent 上。

最终由主 agent 向用户说明整体完成情况、各仓影响、验证结果和仍需明确的事项，不把多个局部成功直接等同于端到端完成。

## 验收顺序

完整流程为：主 agent 设计 → 独立设计 review → 实现与自测 → 独立实现 review 及修复复核 → 主 agent 集成验收 → 按授权交付 PR。具体裁剪遵循前述风险规则。

必要时先用真实小负载核对字段与边界，再按单写入者实施；代码缺陷补能复现问题的回归测试，按风险完成跨仓系统和源码外 wheel 安装验证，纯文档修改不触发昂贵训练。已通过且未受后续改动影响的检查不机械重跑。通用代码习惯见 [Python 开发与验收规范](../standards/python-development.md)。
